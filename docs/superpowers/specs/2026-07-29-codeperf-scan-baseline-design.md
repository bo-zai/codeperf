# CodePerf 扫描基线选择设计

## 背景

当前 `codeperf scan` 的实现虽然是按变更文件扫描，但基线来源仍然带有强假设：默认使用 `origin/master` 作为对比分支。

这个假设在企业代码库里不成立，原因包括：

- 主分支不一定叫 `master`
- 不同仓库可能使用 `main`、`trunk`、`release/*` 或自定义分支
- 开发实际执行流程分为本地验证、pre-push、流水线检查，不同场景需要不同基线
- `git diff` 的含义不唯一，工作区 diff、暂存区 diff、push range diff 不是一回事

因此，问题不在于“要不要用 `git diff`”，而在于“**用哪一个 diff 基线**”。

## 目标

- 去掉 `origin/master` 这类固定主分支假设
- 让 `scan` 在不同场景下自动选择正确的基线
- 保持变更文件扫描模式，不退化为全量扫描
- 让 pre-push 场景尽可能准确表达“本次 push 改了什么”

## 结论

`codeperf scan` 应继续基于 `git diff` 选择扫描文件，但基线选择必须场景化，不能固定为某个分支名。

推荐的基线优先级如下：

1. `pre-push` hook 传入的 `oldSha/newSha`
2. 当前分支的 upstream 对比范围
3. `.codeperf.yml` 中显式配置的 `baseRef/headRef`
4. 本地临时检查场景下的工作区 diff

## 场景定义

### 1. pre-push 场景

这是最重要的正式场景。

- 输入是 hook 提供的 `oldSha/newSha`
- 扫描对象应严格限定为这次 push 范围
- 这类场景最适合做门禁判断

### 2. 本地手动执行场景

开发者在 IDE 或终端里主动执行 `codeperf scan`。

- 如果仓库有 upstream，优先使用 upstream 对比范围
- 如果没有 upstream，再退回到配置中的 `baseRef/headRef`
- 如果只是临时检查工作区变更，可提供工作区 diff 模式

### 3. CI/流水线场景

如果后续仍保留流水线执行：

- 不应依赖某个固定主分支名
- 应优先使用构建系统传入的明确提交范围
- 仅在明确无法获取时，才回退到配置基线

## 不推荐的方案

### 固定 `origin/master`

不推荐。它把仓库治理策略写死进工具，迁移成本高，也容易在多分支项目中误判。

### 直接始终用工作区 `git diff`

不推荐作为正式门禁基线。它只能表达“当前工作区有什么变化”，不能稳定表达“这次提交/推送改了什么”。

### 退化为全量扫描

不推荐。会放大误报和耗时，也不符合 pre-push 及时反馈的目标。

## 设计原则

- 变更范围优先于仓库默认值
- hook 输入优先于配置文件
- 配置文件优先于隐式推断
- 工作区 diff 只作为本地兜底

## 预期效果

- 不再依赖主分支名
- 多开发分支、多仓库策略下都能工作
- 能更准确定位“本次引入的问题”
- 结果更符合真实提交流程，而不是只适配 demo 仓库

## 待确认问题

- 本地手动 `scan` 默认应该优先使用 upstream，还是优先使用配置中的 `baseRef/headRef`
- 当 hook 范围不可用时，是否要显式提示用户当前使用的是回退基线
- 是否需要在报告里展示“本次扫描使用的基线来源”
